# Журнал змін

Розділ про дві різні речі, які легко сплутати: журнал змін самого плагіна — і журнал змін,
який варто вести у **вашому** проєкті, якщо ви публікуєте щось поверх нього (свій SDK,
інструмент, релізи для команди).

---

## Журнал змін плагіна

Лежить у корені плагіна — `CHANGELOG.md`, поруч із `README.md`. Не в `Docs/`, бо це
технічний файл для тих, хто оновлює версію плагіна в уже наявному проєкті, а не частина
навчального посібника.

Формат — [Keep a Changelog](https://keepachangelog.com/en/1.0.0/), версіювання —
[Semantic Versioning](https://semver.org/): `МАЖОРНА.МІНОРНА.ПАТЧ`.

| Компонент | Коли зростає |
|---|---|
| **Мажорна** | API ламається несумісно. Ваш проєкт після оновлення не збереться без правок |
| **Мінорна** | Додано функціонал, стара поведінка не змінилась |
| **Патч** | Виправлення без зміни поведінки, яку хтось міг свідомо використовувати |

Версія плагіна звірена в трьох місцях одночасно — `.uplugin` (`Version` і `VersionName`),
`CHANGELOG.md`, і рядок версії вгорі `README.md`. Синхронізація ручна: якщо після оновлення
плагіна щось не сходиться, вірним джерелом є `CHANGELOG.md` — саме там записано, що́ і чому
змінилося.

Версія `1.0` — перший публічний випуск, тож журнал поки складається з одного запису. Кожен
наступний випуск додаватиме свій **над** ним.

### Як писати запис про виправлений дефект

Найкорисніший запис у журналі — той, у якому читач упізнає свій випадок, не відкриваючи диф.
Ось приклад того, як це виглядає: не «покращено кодування URL», а що саме було зламано, для
кого і як це проявлялося ззовні.

```
- **Object keys containing a space or a non-ASCII character never worked.** The key was
  percent-encoded when building the URL and encoded *again* while signing, so `%20` was
  signed as `%2520`. Every such request came back `SignatureDoesNotMatch`. Encoding now
  happens exactly once, where URLs are built, and the signer treats the path and query as
  final.
```

Три частини, і жодна не зайва: **що не працювало** (ключ із пробілом чи не-ASCII символом),
**як це виглядало для того, хто зіткнувся** (`SignatureDoesNotMatch`, без жодного натяку на
причину), **що змінилося** (кодування тепер рівно один раз). Хтось, хто ловив саме цю помилку
до оновлення, впізнає свій випадок за одне речення — і не мусить читати диф.

## Два шаблони для власного проєкту

Який формат обрати, залежить від того, хто читає журнал і чи є в команди трекер задач.
Нижче — обидва, готові до копіювання.

### Варіант 1 — публічний плагін чи бібліотека без трекера

Читач не має доступу до вашого Jira чи Linear, тож посилання на тікет йому не допоможуть —
корисний лише опис самої зміни. Це саме той формат, яким веде свій журнал і цей плагін.

```markdown
# Changelog

Формат: [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) ·
Версіювання: [Semantic Versioning](https://semver.org/)

## [Unreleased]

### Added
-

## [1.2.0] — 2026-08-15

### Added
- Профілі підключення: можна тримати конфігурацію для декількох бакетів одночасно.

### Fixed
- Завантаження великого файлу на повільному з'єднанні інколи зависало на 99% —
  таймаут очікування останньої частини був коротшим за фактичний час її передавання.

### Changed
- Мінімальна версія рушія — 5.6.

## [1.1.0] — 2026-07-02
...
```

### Варіант 2 — команда з трекером задач

Тут навпаки: читач — це колега, який відкриє журнал уже знаючи проєкт, і посилання на тікет
для нього коштовніше за опис, бо веде до повного обговорення. Класичний формат для внутрішніх
Drupal- і Symfony-проєктів виглядає так:

```markdown
# Change Log
All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](http://keepachangelog.com/)
and this project adheres to [Semantic Versioning](http://semver.org/).

## [Unreleased] - yyyy-mm-dd

Тут пишемо примітки для оновлення — командна робота над тим, щоб зробити їх
максимально простими.

### Added
- [PROJECTNAME-XXXX](http://tickets.projectname.com/browse/PROJECTNAME-XXXX)
  MINOR Назва задачі тут.
- [PROJECTNAME-YYYY](http://tickets.projectname.com/browse/PROJECTNAME-YYYY)
  PATCH Назва задачі тут.

### Changed

### Fixed

## [1.2.4] - 2017-03-15

Тут були б кроки оновлення до 1.2.4 для тих, хто оновлюється.

### Added

### Changed

- [PROJECTNAME-ZZZZ](http://tickets.projectname.com/browse/PROJECTNAME-ZZZZ)
  PATCH Composer тепер бере пакет із Drupal.org.

### Fixed

- [PROJECTNAME-TTTT](http://tickets.projectname.com/browse/PROJECTNAME-TTTT)
  PATCH Видалення runsheet-тизера тепер видаляє й пов'язані картки розкладу.

## [1.2.3] - 2017-03-14

### Changed

### Fixed

- [PROJECTNAME-UUUU](http://tickets.projectname.com/browse/PROJECTNAME-UUUU)
  MINOR Виправлено тести модуля foo.
- [PROJECTNAME-RRRR](http://tickets.projectname.com/browse/PROJECTNAME-RRRR)
  MAJOR Таймлайн модуля foo визначав дату за часовим поясом браузера.
```

Три відмінності від Варіанту 1, і кожна тут не випадково:

- **Тікет перед описом**, а не після — це посилання, а не примітка, і читач вирішує, чи
  переходити за ним, ще до того, як дочитає речення.
- **`MAJOR` / `MINOR` / `PATCH` на рівні окремого запису**, не лише в номері версії вгорі.
  У випуску з десятком змін одразу видно, які саме з них ламають сумісність, без потреби
  зіставляти це з номером версії.
- **Порожні секції лишаються порожніми**, а не видаляються. Це шаблон, який копіюють під
  кожен реліз, і однакова структура означає, що інструмент чи скрипт може покладатися на
  наявність усіх трьох заголовків.

### Яким користуватись

| Ситуація | Варіант |
|---|---|
| Плагін, бібліотека, щось на GitHub без внутрішнього трекера | 1 |
| Команда, кожна зміна вже прив'язана до задачі в Jira/Linear/YouTrack | 2 |
| Немає впевненості | 1 — простіше почати, завжди можна дописати посилання на тікет пізніше |

## Спільні правила для обох варіантів

1. **Пишіть для читача запису, а не для себе тодішнього.** «Виправлено помилку в
   `S3RequestBuilder`» нічого не скаже за півроку. «Ключі з пробілом більше не ламали
   підпис» — скаже одразу.
2. **Один рядок — одна зміна.** Запис на три речення про дві різні речі змушує читача
   розділяти їх самому.
3. **Найважливіше — зверху секції.** Спершу те, що ламало робочі сценарії; дрібні
   косметичні виправлення — насамкінець.
4. **`[Unreleased]` угорі, завжди.** Те, що вже влито в основну гілку, але ще не випущено.
   Під час релізу перейменовуєте його на `[X.Y.Z] — дата` і заводите новий порожній
   `[Unreleased]` над ним — дешевше, ніж писати журнал заднім числом перед кожним випуском.

## Навіщо цей документ тут, а не серед розділів посібника

Журнал змін читають **перед** тим, як оновлювати залежність у робочому проєкті — часто
навіть раніше, ніж саму документацію. Тому посилання на нього винесене нагору, поруч із
назвою й версією, а не поховане серед розділів 1–9: хороший запис відповідає на єдине
питання — «чи торкнеться це зміна мого коду, і як саме» — без потреби читати диф чи
запускати проєкт, щоб з'ясувати.
